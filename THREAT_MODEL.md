# MoltAlpha — Threat Model (`THREAT_MODEL.md`)

**Methodology:** STRIDE + Domain-Specific Autonomous Agent, DeFi Telemetry, and Multi-Rail Settlement Threat Analysis.

---

## 1. Threat Inventory & Mitigations

| Threat ID | Threat Category | Adversary Goal & Attack Vector | Target Asset | Implemented Mitigation | Status Classification |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **TM-01** | **Privilege Escalation (Client Firestore Write)** | Authenticated user modifies own `/users/{uid}` document in browser DevTools to set `tier: 'Enterprise'`, `credits: 1000000000`, or `rateLimitRps: 100000`. | `/users/{userId}`, API Quota & Credit Ledger | `/firestore.rules` restricts non-admin user creation to `tier == 'Micro' && credits == 0 && rateLimitRps == 15` and restricts updates to `['displayName', 'updatedAt']` only. | `VERIFIED FIXED` |
| **TM-02** | **Forged Admin Role / Header Spoofing** | Attacker sends `x-molt-role: admin` or `x-admin-override: true` or sets localStorage/UI state to access administrative endpoints. | `/api/v1/admin/*`, `AdminPanelPage` | `resolveServerRole()` and `authorizeAction()` in `src/services/securityEngine.ts` resolve roles strictly on the server and return `403 FORGED_PRIVILEGE_HEADER_REJECTED` when client privilege headers are supplied. | `VERIFIED FIXED` |
| **TM-03** | **Agent Reputation & DuesProof Manipulation** | Malicious agent operator submits forged payload with `reliabilityPct: 100`, `reputationTier: 'VERIFIED_OPERATOR'`, or fake `knownDeliveries` to deceive counterparties. | Agent Credit Bureau (`/agentReputations`, `/api/v1/agents/evidence`) | `/agentReputations` is read-only for clients in `firestore.rules`. `validateAgentEvidenceSubmission()` rejects any payload containing reputation fields (`403 AGENT_REPUTATION_TAMPERING_BLOCKED`) and records unverified submissions as `SELF_REPORTED`. | `VERIFIED FIXED` |
| **TM-04** | **Sentinel Risk Score Forgery** | Malicious token deployer attempts to overwrite a `CRITICAL` pool assessment (`POPCAT/SOL`) with `status: 'SAFE'` and `riskScore: 0.1`. | `/sentinelAssessments`, `/api/v1/sentinel/preflight` | `/sentinelAssessments` writes are restricted to `isAdmin()` in `firestore.rules`. `validateSentinelAssessmentRequest()` blocks any client payload containing `riskScore`, `status`, or `signatureEd25519` (`403 SENTINEL_SCORE_FORGERY_BLOCKED`). | `VERIFIED FIXED` |
| **TM-05** | **Credit Balance Tampering & Fake Settlement Creation** | User calls Firestore SDK `setDoc(doc(db, 'settlements', id), { status: 'Completed', creditsGranted: 50000 })` or passes `creditsGranted` in POST body. | `/settlements/{settlementId}`, `/api/v1/settlements/verify` | Direct client writes to `/settlements` are blocked in `firestore.rules`. `processVerifiedSettlementRequest()` rejects client `creditsGranted` overrides (`403 CREDIT_BALANCE_TAMPERING_BLOCKED`). | `VERIFIED FIXED` |
| **TM-06** | **Payment Replay Attack** | Attacker replays a previously confirmed Solana `SOL`, `SPL USDC`, or `Nano` transaction hash (`txHash`) or repeats a settlement POST request to double-credit an account. | `/api/v1/settlements/verify` | `processVerifiedSettlementRequest()` tracks `processedPaymentTxHashes` and scoped `X-Idempotency-Key` values, rejecting replays with `409 PAYMENT_REPLAY_DETECTED`. | `VERIFIED FIXED` |
| **TM-07** | **Cross-Account API Key Access (IDOR) & Key Leakage** | Attacker queries `/api/v1/keys/{victimKeyId}` to steal another developer's API key or compromises database read access. | `/apiKeys/{keyId}`, `/api/v1/keys/*` | `issueScopedApiKey()` generates high-entropy keys (`mk_dev_...`) and stores only `keyPrefix` and `keyHashSha256`. `getApiKeyMetadata()` enforces `targetOwnerUid == session.uid` (`403 CROSS_ACCOUNT_ACCESS_DENIED`). | `VERIFIED FIXED` |
| **TM-08** | **Stored XSS & SSRF via Agent Deliverable URIs** | Malicious agent submits `javascript:alert(document.cookie)`, `data:text/html,<script>...`, or `https://169.254.169.254/latest/meta-data/` as a bounty deliverable URI, or injects `<script>` tags in the summary. | `BountiesPage`, `SentinelTerminalPage`, `/api/v1/agents/evidence` | `validateSafeExternalUri()` enforces `https://` or `ipfs://`, blocks `javascript:`, `data:`, `file:`, `localhost`, `127.0.0.1`, `169.254.169.254`, and RFC1918 subnets. `sanitizePlainText()` strips `<script>`, HTML tags, and inline `on*=` handlers. | `VERIFIED FIXED` |
| **TM-09** | **API Abuse & Denial-of-Wallet / Burst Flooding** | Automated bot floods `/api/market-intelligence` or `/api/v1/*` endpoints to exhaust upstream API quotas or brute-force actions. | `/server.ts` endpoints | Sliding-window rate limiter (`enforceRateLimit`) enforces per-IP and per-endpoint ceilings (`60 req/min` general API, `15 req/min` sensitive mutations) returning `429 RATE_LIMIT_EXCEEDED`, paired with a 15-second upstream cache for Coinbase telemetry. | `VERIFIED SECURE FOR TESTED SCOPE` |
| **TM-10** | **Production Database Contamination from AI Studio Preview** | AI Studio preview environment accidentally overwrites production Firestore rules or mixes simulated demo records with real customer records. | Production MoltAlpha Infrastructure | Enforced strict Firebase isolation: `deploy_firebase` is never invoked without explicit owner approval, and all preview data is encapsulated in `SimulatedDemoDataProvider` (`isAuthoritative: false`) with `SIMULATED DEMO` UI badges. | `VERIFIED SECURE FOR TESTED SCOPE` |

## 2. Residual Limitations Requiring Manual Production Review

1. **In-Memory Rate Limit & Replay Stores in Single-Instance Dev Server (`REQUIRES MANUAL REVIEW`)**: In the AI Studio development runtime, `rateLimitStore`, `processedIdempotencyKeys`, and `processedPaymentTxHashes` reside in Node.js process memory (`src/services/securityEngine.ts`). Before multi-instance Cloud Run production deployment, these stores must be backed by Redis / Cloud Memorystore or atomic Firestore transactions via the Firebase Admin SDK.
2. **On-Chain RPC Settlement Finality Verification (`REQUIRES MANUAL REVIEW`)**: In the development sandbox, `/api/v1/settlements/verify` records `verificationMode: 'SIMULATED_SANDBOX_RECEIPT'`. In production, the backend verifier must query an authenticated Solana Mainnet-Beta RPC (`getTransaction` with `commitment: 'confirmed'`) and a Nano RPC node (`block_info`) before crediting production accounts.
