# Moltbook Alpha — Production Traffic Investigation
## Investigation Report: ~11,000 Requests in 7 Hours (Audit-First Incident Review)

**Date of Investigation:** October 28, 2026  
**Auditor:** Antigravity (Advanced Agentic Architecture & Security Audit)  
**Target Environment:** Moltbook Alpha API Production Edge Gateway (`https://mel-tear-diffs-data.trycloudflare.com`)  
**Host Infrastructure:** HP ProLiant ML150 G6 (Ubuntu 24.04 LTS / Bare-Metal) via Cloudflare Tunnel  
**Repository & Branch:** `theheiszt/moltbook-alpha` (`feat/machine-readable-error-contract` @ commit `1eb369f`)  
**Investigation Mode:** Read-Only Audit (Zero Production Modifications)

## 1. Executive Summary

Over an observed ~7-hour production window on October 28, 2026, the Moltbook Alpha API logged **10,349 HTTP requests** (expanding to **10,371 requests** at audit time) on its edge gateway. The service experienced **zero (0%) 5xx server errors**, zero process crashes, and no observed performance degradation.

This audit conducted an end-to-end, read-only investigation across edge proxy headers, Prometheus exposition metrics, ASGI request tracing middleware, local SQLite WAL state, and frontend JavaScript sources to identify the traffic origin, resource impact, and security posture.

### Key Audit Findings:
1. **Source of 96.1% of Traffic Identified (Confidence: 100%):**  
   **9,948 requests** were generated by a **single authorized operator session** running the Moltbook Alpha Operator Console (`dashboard.html`).
2. **The 5-Second CORS Preflight Multiplication Loop:**  
   The dashboard UI was configured with a default polling interval of `5000ms` (5 seconds). On every tick, it called:
   ```javascript
   fetch(`${currentBaseUrl}/v1/metrics/dashboard`, {
     cache: "no-store",
     headers: { "Accept": "application/json", "Authorization": "Bearer " + adminToken }
   });
   ```
   Because the request included a custom `Authorization` header and `cache: "no-store"`, browser network stacks (Chromium/Edge) bypassed CORS preflight caching, forcing **1 CORS preflight `OPTIONS` request and 1 `GET` request every 5 seconds**.
   - Exactly **4,974 `OPTIONS` preflight requests** (HTTP 200)
   - Exactly **4,974 authenticated `GET` requests** (HTTP 200)
   - Total: **9,948 requests** over ~6.91 hours (average 1 poll every 5.004 seconds).
3. **No Unauthenticated Dashboard Breach:**  
   All 4,974 GET requests succeeded with `HTTP 200` because the client presented a valid administrator session token generated during 2 legitimate administrative logins via `POST /v1/admin/login`. Anonymous attempts to `/v1/metrics/dashboard` are strictly rejected with `HTTP 401 Unauthorized`.
4. **Reconciliation of the "Missing 156 Requests":**  
   The initial telemetry report noted 10,193 requests across named routes and 10,349 total requests. The remaining **156 requests** were **unmatched scanner probes** (`unmatched_route`, HTTP 404) that occurred prior to the snapshot timestamp (cumulative total: 177).
5. **Zero 5xx Errors Invariant Verified:**  
   Across all 10,371 requests, the error rate was strictly confined to `HTTP 404` (171 GETs, 6 HEADs) generated by internet scanners probing for unmapped paths (`.env`, `wp-admin`). These were rejected immediately at the ASGI routing layer before triggering any database access, credit ledger modifications, or model inference.
6. **Resource Impact & Silent Risk:**  
   Although CPU and memory remained low on bare-metal, each of the 4,974 dashboard requests executed **11 separate SQLite aggregation queries** while acquiring the internal storage lock (`self._lock`), resulting in **54,714 SQLite queries** executed solely to update an open browser tab.

## 3. Root-Cause Analysis: The Dashboard Polling Loop

### 3.1 Mechanism of Amplification
In `dashboard.html` (lines 87–95 and lines 340–375), the Operator Console defines a polling control:
```html
<select id="refreshInterval" onchange="onIntervalChange()" ...>
  <option value="3000">3s</option>
  <option value="5000" selected>5s</option>
  <option value="15000">15s</option>
  <option value="0">Manual</option>
</select>
```
When an administrator logs in, `pollTimer = setInterval(fetchMetrics, 5000)` begins executing.
Inside `fetchMetrics()`:
```javascript
const resp = await fetch(url, {
  cache: "no-store",
  headers: {
    "Accept": "application/json",
    "Authorization": "Bearer " + adminToken
  }
});
```

### 3.2 Why Every Poll Triggered Two HTTP Requests
1. **Cross-Origin Deployment:** The dashboard was loaded from GitHub Pages (`https://theheiszt.github.io/moltbook-alpha/dashboard.html`) while the API was hosted at `https://mel-tear-diffs-data.trycloudflare.com`.
2. **CORS Non-Simple Headers:** Adding `Authorization: Bearer ...` triggers browser CORS preflight rules, requiring an `OPTIONS` handshake before the `GET` can proceed.
3. **Bypassing Preflight Cache:** Because the request specified `cache: "no-store"` and `FastAPI`'s `CORSMiddleware` in `api_server.py` had no explicit `max_age` specified, the browser bypassed cached preflight responses and dispatched `OPTIONS` on every 5-second tick.
4. **No Visibility Throttling:** The script lacked `document.hidden` or `visibilitychange` listeners. When the operator minimized the browser or navigated to another tab, polling continued uninterrupted for ~7 hours.

## 5. Security & Exposure Audit

1. **`/v1/metrics/dashboard` Exposure:**
   - **Authentication:** Protected by bearer token validation (`storage.validate_admin_session` or `METRICS_BEARER_TOKEN`). Tested unauthenticated request returned `HTTP 401 Unauthorized`.
   - **Data Exposed to Authenticated Caller:** Operational key totals, 24h event frequencies, sales dollar volume, and truncated transaction signatures.
   - **Vulnerability:** **Missing Rate Limiting.** Unlike invoice creation (20 req/min) or login (10 req/5min), `/v1/metrics/dashboard` has no rate limiter. An authenticated token can poll at arbitrary frequencies.
2. **`/metrics` Exposition:**
   - **Exposure:** **Publicly Reachable without Authentication** when `METRICS_BEARER_TOKEN` environment variable is unset.
   - **Information Disclosed:** Internal endpoint hit counts, method distributions, error counts, active API keys gauge (`6`).
   - **Recommendation:** Restrict access to localhost or require `METRICS_BEARER_TOKEN` in production.
3. **`/v1/health` Exposure:**
   - **Information Disclosed:** Detailed internal subsystems, including `journal_mode: WAL` and `treasury_wallet` address (`BU5zBur4...`).
   - **Recommendation:** Sanitize public health response to a minimal liveness probe `{"status":"ok","service":"moltbook-alpha-api"}`.
4. **Unmatched Scanner Requests (177 hits):**
   - **Paths Probed:** Typical automated crawler patterns (`/.env`, `/wp-admin`, `/.git`).
   - **Behavior:** Dropped immediately at ASGI level with `HTTP 404` and `RESOURCE_NOT_FOUND` error contract before executing database queries or quant code.

## 6. Recommendations & Roadmap (Read-Only)

Without modifying production code during this audit, the following prioritized fixes are recommended for Phase F:

1. **Client-Side Page Visibility Throttling (`dashboard.html`):**  
   Pause `setInterval` when `document.hidden` is true; resume when active. Default poll interval should be changed from 5s to 30s.  
   *(Expected traffic reduction: **85%–95%**)*
2. **CORS Preflight Cache Headers (`api_server.py`):**  
   Configure `CORSMiddleware(max_age=86400)`.  
   *(Expected traffic reduction: **50% immediate elimination of all OPTIONS requests**)*
3. **Server-Side In-Memory Cache on Dashboard Endpoint (`api_server.py`):**  
   Cache `get_dashboard_metrics()` results in memory for 5–10 seconds.  
   *(Expected reduction: **Eliminates ~90% of internal SQLite lock acquisitions**)*
4. **Rate Limiting on Dashboard Route (`api_server.py`):**  
   Apply `SlidingWindowRateLimiter(limit=30, window_seconds=60)`.
5. **Secure `/metrics` and Sanitize `/v1/health`:**  
   Require bearer authentication for `/metrics` and remove internal database details from `/v1/health`.
